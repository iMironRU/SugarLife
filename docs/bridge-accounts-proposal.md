# Предложение к контракту моста: аккаунты производителя и хранение секретов

Статус: **черновик, для обсуждения с ядром** (sugarlife-core / KMP-движок).
Связанное: CONNECT-UX §2b (устройства × способы), §7a (каталог требований),
`app/src/domain/requirementsCatalog.ts`, `app/src/sections/DeviceSection.tsx`.

## Зачем

Части сенсоров для работы нужен **аккаунт в облаке производителя** — Ottai и подобные. Без
входа железка не отдаёт данные вовсе. Сейчас выразить это нечем ни в контракте, ни у нас:
в каталоге требований поддержка описана как `direct | bridge | blocked`, а требование — строкой
для человека (`'радиомост OrangeLink/RileyLink'`), которую интерфейс подхватить не может.

## Почему это способ, а не параметр устройства

В §2b способов четыре: прямое / мост / облако / вручную, где «облако» — наш Nightscout.
Аккаунт производителя по смыслу другое: это не хаб наших данных, а **предусловие работы самой
железки**. Отсюда три следствия:

1. У него своё состояние, отдельное от связи с устройством: не подключён / вошли / вход истёк.
2. Один аккаунт обслуживает **несколько** сенсоров той же марки — значит это отдельная сущность,
   а не поле устройства.
3. В каталоге требований нужен свой вид поддержки: «работает, но нужен аккаунт производителя» —
   это не то же самое, что `direct`, и совсем не `blocked`.

## Что предлагается (аддитивно)

```ts
/** Внешняя учётка, от которой зависит работа устройств (облако производителя сенсора). */
export interface Account {
  id: string;
  vendor: string;                 // 'ottai'
  displayName: string;            // «Ottai»
  state: 'NotLinked' | 'Linked' | 'Expired' | 'Error';
  settings: SettingsSpec;         // чем входят: логин/пароль/регион/OAuth
  devices: string[];              // id устройств, которым эта учётка нужна
  problem?: Problem | null;
}

export interface UiSnapshot {
  // ...существующие поля...
  accounts?: Account[];
}

export type Intent =
  // ...существующие...
  | { type: 'linkAccount'; accountId: string; params: Record<string, string> }
  | { type: 'unlinkAccount'; accountId: string };
```

И в `DeviceInfo` — ссылка на требуемую учётку, чтобы карточка устройства могла честно сказать
«нужен вход», не гадая:

```ts
requiresAccountId?: string | null;
```

## Секреты — отдельный пункт, и он важнее остального

Пароль от аккаунта производителя **нельзя** класть в localStorage. Ему место в Keychain/Keystore
на нативной стороне: PWA собирает значение и отдаёт через интент, обратно в снимок оно не
возвращается **никогда**.

Просьба зафиксировать это в контракте явно, а не по договорённости:

- `Param` с `type: 'Secret'` — **только на запись**. В `SettingsSpec`, приходящем в снимке,
  у такого параметра `default` всегда `null`, даже если значение задано.
- Снимок отдаёт лишь факт «задано / не задано» (это уже покрывается `Account.state`).

Практическое следствие для нас: в браузере без нативного моста безопасного места нет вовсе.
Значит вендорский аккаунт в браузерной версии либо недоступен, либо честно помечен «работает
только в приложении». Хотелось бы понимать вашу позицию до того, как мы нарисуем интерфейс.

## Что PWA делает до принятия

Расширяем каталог требований своим видом поддержки (`vendorCloud`) и показываем способ «облако
производителя» с состоянием «нужен вход». Хранение секретов до появления нативного моста **не
делаем вовсе** — лучше показать «работает только в приложении», чем положить пароль в браузер.
