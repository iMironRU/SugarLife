# Предложение к контракту моста: состояние записи в реестре

Статус: **черновик, для обсуждения с ядром** (sugarlife-core / KMP-движок).
Связанное: `docs/CONNECT-UX.md` §2a (реестр), §2b (устройства × способы), `app/src/data/bridge.ts`.

## Зачем

По CONNECT-UX §2a устройство — это **запись в инвентаре**, а связь — лишь одно из её состояний:

```
Записано → Настроено → На связи / На паузе → Забыто
```

Контракт моста (rev 1.6) этот жизненный цикл выразить не может:

- `DeviceInfo.connection: Link` — это `Disconnected | Connecting | Connected | Streaming | Error`,
  то есть **только живой линк**. «Записано, но ещё ни разу не подключалось» и «настроено, но мост
  не выбран» в него не помещаются — оба выглядят как `Disconnected`.
- В `DeviceInfo` нет идентичности драйвера/модели, которая могла бы **отсутствовать**. Устройство
  в контракте существует потому, что добавили драйвер.
- Интент `addDevice` требует `driverType: string`. Записать железку, **модель которой неизвестна**,
  нечем.

## Практический случай, который это ломает

Штатный сценарий онбординга: человек подключил Nightscout, оттуда идут глюкоза и статус помпы.
Данные есть — а какая именно у него помпа и какой сенсор, он не назвал (не знает / не хочет сейчас).

Это не ошибка и не полумера: пока модель неизвестна, **единственный честный способ для устройства —
облако**, потому что мы не можем знать, нужен ли этой железке мост или она вещает напрямую.
Как только модель указана — открываются прямое чтение и мост (по каталогу требований §7a).

То есть «модель неизвестна» — это **легитимное состояние реестра**, определяющее набор доступных
способов, а не временная дырка в данных.

## Что предлагается (аддитивно, старые мосты не ломаются)

```ts
export interface DeviceInfo {
  // ...существующие поля...

  // Жизненный цикл записи (§2a) — ортогонален живому линку `connection`.
  registryState?: 'Recorded' | 'Configured' | 'Linked' | 'Paused';

  // Модель/драйвер записи. null = запись есть, модель неизвестна → доступен только сервис-способ.
  driverId?: string | null;
}
```

И возможность записать устройство без драйвера — либо ослабить существующий интент:

```ts
| { type: 'addDevice'; driverType: string | null; params: Record<string, string>; mode?: 'attach' | 'activate' }
```

либо ввести отдельный:

```ts
| { type: 'recordDevice'; kind: 'sensor' | 'pump'; driverType: string | null }
```

Отдельный интент выглядит честнее: `addDevice` семантически про «подключить», а тут именно
«записать в инвентарь, подключу позже» (§7a, путь 13).

## Как это сейчас живёт в PWA

До расширения контракта состояние держится локально в `app/src/data/deviceConfig.ts`:

| Значение `pumpId`/`sensorId` | Смысл | Доступные способы |
|---|---|---|
| `null` | записи нет | — |
| `'unknown'` (`UNKNOWN_MODEL`) | запись есть, модель не указана | только облако |
| `<id модели>` | запись есть, модель известна | облако + прямое/мост |

Отображается через `deviceStatus()` → `unset | unknownModel | needsBridge | configured`.

Это **временная локальная реализация**. Когда ядро начнёт владеть реестром, состояние должно
приехать из `snapshot.devices[]`, а не считаться в PWA — поэтому важно, чтобы словарь совпал
заранее, а не расходился.
